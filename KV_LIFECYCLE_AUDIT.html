KV Lifecycle Audit

Research question

Given what the harness knew at the time, was the GPU or memory system doing the wrong work at the wrong time?

Join tool waits and session lifetimes to observed cache, transfer, request, and batch activity. Distinguish useful work, reasonable insurance, mistimed work, and potentially wasted work. Test whether a feasible alternative improves the whole system before claiming avoidable harm or a hardware opportunity. This is an audit of timing and placement, not just HBM bandwidth interference.

Five audit ledgers

  • Host backupsHost residency and load-back observed; useful versus insurance versus wasted backup not yet graded.
  • GPU evictionsForced eviction observed; capacity necessity and avoidability not yet graded.
  • Session resumesPartial live timing evidence for prepared-during-wait versus after-wait load; competing-session cost unmeasured.
  • HBM occupancyUseful, idle, and dead block-seconds not yet measured.
  • GPU timeUseful compute, recompute, and idle-with-stageable-work not yet measured.

Question tested. When differently timed but equally important agent sessions overlap, which cache events happen before or after each replay becomes ready?

How it ran. nvidia_a10g_24gb; Qwen/Qwen2.5-Coder-7B-Instruct; backend 0.5.10.post1; trace kv_lifecycle_lean. Three equal-importance sessions began together. Two tool waits overlapped; the third session ended without replay. An explicit control command evicted the long-wait session's GPU prefix under a synthetic two-prefix budget, then the client proved host residency. Its load was requested when the tool returned without gating replay on the control response. Prompt target: 4090 words; output cap: 16 tokens; host cache: 8 GB; GPU memory fraction: 0.7. No frontend task had higher semantic priority.

Observed. The short-wait replay and long-wait replay came from different sessions. The long session's GPU prefix was explicitly evicted and proved host-resident before its tool returned.

  • Long session was explicitly evicted to host and later underwent a native load
  • The short and long tool waits overlapped
  • One session ended without replay

Short tool return→submission: 0.1 ms; replay TTFT: 81.5 ms; cached prefix: 4177 tokens.

Long tool return→submission: 0.4 ms; replay TTFT: 282.0 ms; cached prefix: 4177 tokens; second replay cached prefix: 4194 tokens.

Long session's load request / acceptance / observed completion after tool return: 0.1 ms / 177.5 ms / 179.4 ms. These timestamps locate work; they do not by themselves assign a causal delay.

Plausibly mistimed.

  • Host-backed load was not requested until the long tool call returned; an earlier request was possible in this trace, but its effect under the same load is unmeasured

Avoidable work. unknown: no same-capacity, same-load counterfactual was run
