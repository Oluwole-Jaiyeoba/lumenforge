Controller Policy Results

A reproducible record of controller experiments. The JSON registry is the machine-readable source of truth; this page is generated from it.

Active Protocol

Scenario 1 gives every request equal application importance. Harnesses provide expected tool-return times; the controller derives temporary backend queue ranks. Historical records below are retained as evidence, not as current reproduction instructions.

Other Research Lanes

Harness Signal Benchmark records native harness signal emission. GPU Interference tracks controlled GPU measurements. Neither is evidence for the controller results below.

Comparison Safety

  • Compared modes must use the same workload timeline and request population.
  • The active Scenario 1 protocol forbids application-level priority classes; numeric backend ranks may only be derived from replay-ready time.
  • Controller capabilities must be isolated unless the record explicitly names a combination.
  • A valid result requires trace coverage and no client-side replay-dispatch delay dominating the outcome.

scenario1_equal_importance_active

Scenario 1: Equal-Importance Ready-Time Scheduling

Validated reference

Can expected tool-return times improve replay scheduling when no task is designated more important by the front end?

Controller scope

Ready-time ordering and safe GPU backfill only; backend priority numbers are temporary queue ranks derived by the controller.

Priority contract

All 16 sessions have equal application importance. Both former target-role and filler-role replays have deadlines. No front-end priority, QoS tier, urgent label, or demotable background class is allowed.

Compared modes

no_prefetch vs controller_ready_time_gpu_backfill

Workload

DeepAgents; P3; 16 sessions x 2 replay steps = 32 deadline-bearing replays per mode; identical seeded workload shape.
