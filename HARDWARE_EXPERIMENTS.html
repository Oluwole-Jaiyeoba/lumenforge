KV Movement Interference

Does host-to-GPU KV movement delay replay or ongoing token generation?

Measured - review pending
Platform
nvidia_standard; record the exact GPU in the run manifest
Backend
pinned 0.5.10.post1 runtime and selected adapter
Control
Replay and decode without competing host-to-GPU KV movement.
Interference
Identical replay and decode timeline while other KV data moves to the GPU.
Held constant
Model, request population, prompt/output lengths, seed, backend flags, and cache state.

Measurements

  • Replay ready-to-first-token time and deadline lateness
  • Decode inter-token latency, including tail latency
  • KV transfer start, end, bytes, and overlap with replay
  • Physical transfer and memory activity in a separate profiler pass

Evidence rule: Backend KV events show software-visible movement; physical saturation needs profiler or hardware-counter evidence. Lightweight and profiled timing runs are not pooled.

Sustained Decode KV Overlap

Does native host-to-GPU KV load-back slow an already-running decode?

Measured - review pending
Platform
nvidia_standard; NVIDIA A10G 24 GB in this sanity run
Backend
SGLang 0.5.10.post1 in the pinned container runtime with the v0510 adapter
Control
Decode a fixed 256-token response after staging a host-resident donor prefix, without reloading that prefix during decode.
Interference
Start the same decode, wait for 24 visible streamed updates, then reload 4,039 donor-prefix KV tokens from host memory to GPU through SGLang's native HiCache path.
Held constant
Model, prompt and output lengths, seed, backend flags, donor prefix, cache-staging procedure, and equal frontend request treatment.

Measurements

  • Decode time to first token and total decode duration
  • Visible streamed-update intervals before, during, and after load-back
  • Native CUDA-event load duration and loaded-token count
  • Software-timeline proof that load-back occurred after decode started and before it completed

Evidence rule: This sanity run proves native load-back and software-visible overlap. A repeated paired run is required before claiming a causal latency effect, and a separate profiler pass is required before claiming physical memory-bandwidth contention.

Sustained KV Pressure During Decode

Does a sustained train of native host-to-GPU KV reloads measurably slow an already-running decode?

Measured - review pending
Platform
nvidia_standard; NVIDIA A10G 24 GB in this sanity run
Backend
SGLang 0.5.10.post1 in the pinned container runtime with the v0510 adapter
Control
Decode a fixed 256-token response after staging eight host-resident donor prefixes, without reloading donors during decode.
Interference
After 24 visible decode updates, reload either one donor or all eight donors sequentially through SGLang's native HiCache path.
Held constant
Model, target prompt and output length, seed, backend flags, donor pool, cache-staging procedure, 40,000-token device-cache preparation, and equal frontend request treatment.

Measurements

  • Decode time to first token and total decode duration
  • Visible streamed-update intervals before, during, and after the reload train
  • Native CUDA-event duration and loaded-token count for every reload
  • Software-timeline proof that every reload window intersected active decode

Evidence rule: Every native load must finish inside decode, have positive CUDA duration, and intersect a client-visible decode interval. This one-pair sanity run proves the mechanism; repeated paired trials and a separate profiler pass are required for causal and physical-bandwidth claims.

KV Pressure Duty Sweep

How does verified host-to-GPU KV reload pressure change the duration of an already-running decode?

Validated result
Platform
nvidia_standard; NVIDIA A10G 24 GB
Backend
SGLang 0.5.10.post1 in the pinned container runtime with the v0510 adapter
Control
Decode a fixed 384-token response after staging eight host-resident donor prefixes, without native reloads during decode.
Interference
After 24 visible decode updates, reload 20, 60, or 100 host-backed donor prefixes through SGLang's native HiCache path.
Held constant
Model, prompt and output length, seed, backend flags, donor pool, cache-staging method, device-cache preparation, and equal frontend request treatment.
Production analogy
One agent is decoding while several other suspended agent sessions resume and need their host-resident KV context returned to GPU memory.
What this establishes
At higher measured native reload pressure, ongoing decode became consistently slower across three paired samples.
Limit
This controlled workload proves interference from native KV reloads, but does not by itself isolate HBM bandwidth from copy-engine, cache, or stream-scheduling effects.

Measurements

  • Time to first token and total decode duration
  • Native CUDA load duration, copied token slots, and native-copy share of decode
  • Proof that each requested load completed during active decode
  • Paired decode-duration change versus the matching control sample

Evidence rule: Every requested native load must have positive CUDA duration, finish during active decode, intersect a visible decode interval, and retain a host-backed donor copy when recycled.

Natural Multi-Agent KV Pressure

Under a production-shaped, equal-priority agent workload, how often do normal session replays naturally reload host-resident KV while another session is decoding?

Planned - not measured
Platform
nvidia_standard; record the exact GPU in the run manifest
Backend
pinned 0.5.10.post1 runtime and selected adapter
Control
Ordinary equal-priority session replays after tool waits. The runner does not issue prepared-prefix control requests or synthetic reload commands.
Interference
Natural cache pressure caused only by concurrent sessions building context, waiting for tools, and resuming through ordinary replay requests.
Held constant
Model, session count, tool-wait distribution, context and output lengths, stagger, backend flags, and seed where applicable.
Production analogy
Several coding-agent sessions pause for tools and then resume; some may need host-resident KV returned to GPU while another session is generating.
What this establishes
A measured distribution of native SGLang load-back overlap counts during ordinary replay decodes, not a synthetic transfer injection.
Limit
A natural overlap count is only a provisional mapping to the controlled pressure sweep. A profiler pass is still required to attribute physical bandwidth or copy-engine utilization.

Measurements

  • Per-replay time to first token and total decode duration
  • Native SGLang load-back events overlapping each replay
  • Session and replay correlation for every observed load-back
  • Distribution of observed overlap counts against the controlled reference ranges

Evidence rule: Only native hiradix.load_back.end events tagged with this workload and a replay phase count as natural reloads. The report must retain the event-to-session correlation and state whether no natural reloads were observed.

Replay Behind Active Compute

Planned - not measured
Platform
nvidia_standard; record the exact GPU in the run manifest
Backend
pinned 0.5.10.post1 runtime and selected adapter
Control
The same replay timeline without overlapping prefill work.
Interference
Make replay ready during prefill; vary one prefill chunk-size setting at a time.
Held constant
Model, replay inputs, arrival schedule, seed, backend flags other than chunk size, and request population.

Measurements

  • Replay ready, backend submit, admit, compute start, and first-token times
  • Duration of overlapping active prefill work
  • Replay wait attributable to active compute versus queue or submit gaps
  • Prefill throughput and decode inter-token latency

Evidence rule: A long replay wait alone does not prove GPU compute blocking; align backend stage events with a GPU execution timeline. Lightweight and profiled timing runs are not pooled.
