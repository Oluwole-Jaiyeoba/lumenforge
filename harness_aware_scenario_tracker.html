Core Research Idea

This research asks whether agentic LLM serving can improve when the backend is not blind to the surrounding workflow or the physical GPU state. The goal is to combine three kinds of visibility: what the harness knows will happen soon, what SGLang knows is happening now, and what the hardware is physically experiencing.

Harness / front end
what will matter soon

Examples: session identity, tool-wait phase, expected replay-ready time, prefix identity, and reuse intent.

SGLang / runtime
what is queued or running now

Examples: local gate state, SGLang scheduler priority, prefill/decode state, KV residency, and TTFT.

Hardware telemetry
what the GPU is physically experiencing

Examples: GPU utilization, idle windows, memory pressure, bandwidth pressure, throttling, and device headroom.

Simple meaning: the harness predicts future replay needs, SGLang explains the serving path, and hardware telemetry tells the controller whether the GPU has safe physical room for more work.

Why combine all three? Because each layer sees a different part of the truth. The harness knows future workflow intent, SGLang knows the logical serving path, and hardware telemetry knows the physical limits of the GPU. A controller that sees only one layer can make locally reasonable decisions that are globally bad.

Why harness visibility?
tokens alone do not reveal future intent

The backend cannot infer from token shape that a tool call is about to return, that a prefix will likely be reused, or that a session is still relevant.

Why SGLang visibility?
decisions must reach the real serving path

SGLang tells us whether work was queued, admitted, cached, evicted, delayed, or actually served with the intended priority.

Why hardware visibility?
logical state is not physical state

The queue can look safe while the GPU is saturated, or conservative while the GPU has idle headroom that could be used safely.

Experiment Rule

For each scenario, start with two modes only: a baseline where the backend does not receive the harness signal, and a harness-aware controller mode where the backend uses the signal to make the smarter decision. Add diagnostic modes only when the two-mode story does not explain the result.

Before any new real experiment, coordinate with the backend task to reuse the established SGLang scripts, hooks, modes, and proof columns.

After every scenario run finishes, update this tracker with the latest result cards, a short interpretation, and links to the detailed report and proof files.

How the experiment is set up

Scenario 1: Better Deadline Scheduling

Clear Win

A group of replay requests becomes ready at different times after tool waits. The harness exposes when each replay is expected to become ready, so the backend can move the soonest-due replay work forward instead of treating the workload as ordinary queue traffic.

How the experiment is set up

The same 32 replay requests are run in both modes using the same generated timeline. Tool waits are sampled from realistic buckets, so some replays return quickly and others return much later. In baseline mode, replay submissions use ordinary behavior. In RTG controller mode, the harness exposes replay timing during tool wait; the controller assigns ready-time priority before replay, uses that priority in the local submission gate, lowers the same priority into SGLang, and samples GPU idle state to decide whether safe backfill would be allowed.

What the controller does and why this scenario wins

What this setup tests: whether the backend can serve equal-importance replay requests more fairly when it learns each request's expected replay-ready time before the replay arrives.

What the controller does: during tool wait, it predicts when each replay will return, assigns earlier-ready requests stronger scheduling position, applies that order at the local submission gate, and also lowers the same ordering into SGLang's scheduler priority path.

Why this creates a win: baseline SGLang sees work only when it arrives. The controller sees the future replay timeline earlier, so it can avoid letting later-ready work sit in front of sooner-ready replay work. In the latest run, that improved TTFT, lateness, max lateness, and the full replay workload window.

Hardware-telemetry nuance: GPU idle state was sampled in this run, but it did not change admission decisions. The clean win came mainly from ready-time ordering across both the local gate and SGLang scheduler path.

Scenario 2: Proactive KV-Cache Management

Improved + Guarantee Smoke

Many long-context sessions enter tool wait and are likely to resume at different times. The harness exposes each session's identity, reusable prefix, expected return time, reuse likelihood, and recompute cost, so the backend can prepare valuable KV before replay.

In simple words: this scenario checks whether the backend can prepare KV for all soon-returning replay sessions, not just one special target session.

How the experiment is set up

The same 32 replay requests are run in both modes using the same generated timeline. Each replay session has its own session_id and prefix_id. In baseline mode, the backend waits until replay arrives. In controller mode, the harness exposes ETA, reuse probability, and recompute cost during tool wait. The controller requests real SGLang-side KV preparation only when the window is safe enough for the load to finish before replay.

What the controller does and why this scenario wins

What this setup tests: whether the backend can make replay cheaper by preparing useful KV before the replay request arrives.

What the controller does: during tool wait, it uses the harness signals to identify sessions that are likely to reuse a prefix soon and would be expensive to recompute. Before moving anything, it asks SGLang for a plan_only prepare-prefix answer. If the prefix is already on GPU, it skips it. If the prefix is too small or not safely loadable, it skips it. If SGLang says the prefix is evicted from GPU but backed by host KV and worth loading, the controller admits the load.

Important load-path guarantee: the controller is directly loading KV blocks using SGLang's own prepared-prefix / HiCache load_back mechanism. It is not sending fake requests, synthetic prompts, or cache-warming requests and hoping SGLang loads KV as a side effect. The KV movement is done through the same SGLang mechanism that replay would rely on, so SGLang is aware of the host-to-device movement.

Why this creates a win: without the controller, replay may arrive and then pay the reload or rebuild cost while the user is waiting. With the controller, useful host-resident KV can be moved back to GPU before replay arrives, and redundant loads are avoided. That is why the selective-admission run improved total TTFT and total lateness across the workload.

Scenario 3: Better Cache Eviction Decisions

Request Win + Trade-off

All replay-capable requests compete for limited KV capacity. The harness exposes which prefixes are likely to be reused, how expensive they are to rebuild, and when replay is expected, so the backend can tell SGLang which KV is more valuable before eviction pressure hits.

In simple words: this scenario checks whether SGLang can make better eviction choices when the controller gives it value information for every replay-capable request, not just one special target request.

How the experiment is set up

The same 32 replay requests are run in both modes using the same generated timeline. The load generator creates enough concurrent long-context sessions to force KV eviction decisions. In baseline mode, requests run without value-aware eviction signals. In controller mode, every replay-capable prefix is scored as high, normal, or low value from harness signals, and that value is lowered into SGLang priority. SGLang's own priority radix eviction path performs the real eviction.

What the controller does and why this scenario wins

What this setup tests: whether cache eviction gets better when the backend knows which cached prefixes are likely to matter soon and which ones are cheaper to lose.

What the controller does: it translates session_id, prefix_id, replay timing, reuse probability, and recompute cost into controller_eviction_value_class, controller_eviction_value_score, and controller_sglang_priority. High-value prefixes get priority 100, normal prefixes get 0, and low-value prefixes get -100.

Important eviction-path guarantee: the controller does not manually evict KV blocks. It gives SGLang better priority information, and SGLang's native priority radix eviction policy performs the eviction. That keeps SGLang's cache state authoritative.

Why this creates a win: under memory pressure, baseline eviction can discard useful prefixes without knowing their future value. With the controller, SGLang has value-ranked KV, so replay requests spend less total time waiting for first tokens and less time late after tool return. The trade-off in this run is that the total workload window became longer.
